# Story Wiki 稳定基线与可用性闭环优化方案

> 状态：执行中  
> 日期：2026-07-17  
> 建议版本：v0.13.0  
> 优先级：P0  
> 预计工作量：3-5 天

---

## 1. 背景

Story Wiki 已经具备文本分析、Obsidian 笔记生成、关系图谱、小说创作、质量检查、多格式导出、跨作品管理和角色成长分析等能力。当前主要问题已经不是功能不足，而是功能扩张速度超过了工程收口速度。

本轮检查确认：

- 优化前测试共收集 587 项；指定可写临时目录后结果为 `586 passed, 1 failed`
- PDF 测试假设已经修复，并新增 PDF 损坏场景与核心端到端 smoke test；当前为 `589 passed`
- 当前工作区存在一批尚未收口的大规模重构和新增模块
- `pyproject.toml` 没有完整声明运行依赖，README 的安装说明也不完整
- Web UI 已有原型，但未纳入正式依赖、测试和启动流程
- Web 层存在两套重复的 Markdown 解析逻辑，其中备用实现包含拼写错误
- 项目指令指定 mimo-v2.5/token-plan，但代码和部分文档默认仍是 DeepSeek
- 单元测试较多，但缺少覆盖核心业务链路的固定样本端到端验收

因此，下一阶段应停止横向增加功能，先建立稳定、可安装、可验证、可交付的版本基线。

---

## 2. 本阶段目标

### 核心目标

把现有功能从“模块基本齐全”提升到“新环境能够可靠运行，核心链路能够重复验证”。

### 胜利条件

以下条件必须全部满足：

1. 使用标准安装命令可以安装全部核心运行依赖
2. 全量 587 项测试全部通过
3. 固定短文本可以完成一次分析端到端流程
4. 生成的 Markdown 可以被系统重新读取，并形成正确的图谱和时间线数据
5. Web UI 能浏览真实生成结果，并有基础 API 测试保护
6. README、配置文件和实际使用的模型供应商保持一致
7. 当前重构形成清晰版本基线，不再混入无关新功能

---

## 3. 优化范围

### 本阶段包含

- 依赖与安装流程收口
- 测试基线修复
- 核心端到端 smoke test
- Web UI 最小只读闭环

### 本阶段不包含

这些工作不是没有价值，而是必须等稳定基线完成后再评估。

## 4. 执行任务

## P0-1：建立可复现的安装方式

### 现状

`pyproject.toml` 只包含项目元数据和测试配置，没有声明运行依赖。README 当前只提示安装 `requests` 和 `psutil`，无法覆盖 EPUB、PDF、YAML 和 Web UI。

### 改动

在 `pyproject.toml` 中声明：

- 核心依赖：`requests`、`psutil`
- 分析格式依赖：`ebooklib`、`pymupdf`
- Web 依赖：`fastapi`、`uvicorn`、`pyyaml`
- 测试可选依赖：`pytest`、`pytest-cov`、`pytest-mock`、`httpx`

根据实际使用方式决定 EPUB/PDF/Web 是否作为 optional dependency 分组。推荐：默认安装核心分析能力，Web 使用 `web` 可选分组，测试使用 `test` 分组。

### 验收标准

- 新虚拟环境中可以完成标准安装
- `python -c "import src"` 成功
- CLI 帮助命令可以启动
- Web 可选依赖安装后，FastAPI 应用可以导入
- README 中只保留一种推荐安装方式

## P0-2：恢复全绿测试基线

### 现状

指定项目内临时目录后，全量测试结果为：

```text
586 passed, 1 failed
```

失败测试：

```text
tests/test_extractor.py::TestExtractTextPdf::test_pdf_without_pymupdf_raises
```

测试创建了伪 PDF，但在已安装 pymupdf 的环境中仍期待“未安装 pymupdf”错误。测试名称和测试行为不一致。

### 改动

将 PDF 测试拆为两个明确场景：

1. mock 导入失败，验证未安装 pymupdf 时给出可理解的安装提示
2. pymupdf 已安装但文件损坏，验证系统将底层格式错误转换成明确的业务错误

同时在 pytest 配置中指定稳定的临时目录策略，避免 Windows 系统临时目录权限导致大量伪错误。

### 验收标准

- `python -m pytest tests/ -q` 在标准开发环境中为 `587 passed`
- 不依赖开发者机器是否已经安装可选格式库
- 损坏的 EPUB/PDF 都返回清楚、稳定的错误信息

## P0-3：增加核心端到端 smoke test

### 目标链路

```text
固定短文本
  -> 文本提取
  -> 章节切分
  -> AI 结构化结果（固定 mock 响应）
  -> 合并去重
  -> Obsidian Markdown 生成
  -> VaultManager 重新读取
  -> 验证人物、关系、事件、设定和 wikilink
```

### 设计原则

- 使用 1-2 章、约 1000-3000 字的固定中文样本
- AI 返回使用固定 fixture，不调用真实 API
- 只验证最关键的数据契约，不追求覆盖所有异常分支
- 输出写入 pytest 临时目录，不触碰真实 Obsidian Vault

### 必须验证

- 至少生成 2 个人物、1 个设定和 1 个事件
- 人物 frontmatter 字段正确
- 人物关系 wikilink 指向存在的卡片
- 事件参与者和地点链接正确
- VaultManager 可以重新读取生成结果
- 同名人物不会因章节合并产生重复卡片

### 验收标准

- 新增一个稳定、快速、不联网的端到端测试
- 入口、生成器和读取器任一数据契约被破坏时，测试能够失败

## P1-1：收口 Web UI 最小 Demo

### 当前问题

- `web/app.py` 已自行实现一套 Markdown 解析逻辑
- `web/parsers.py` 又实现了另一套相似逻辑
- `web/parsers.py` 中存在 `rplit` 拼写错误
- `web/parsers.py` 当前没有被应用层使用
- Web 路由没有自动化测试
- 输出目录固定为 `data/output`，缺少统一配置入口
- 缓存没有失效机制，文件更新后可能继续返回旧数据

### 推荐结构

```text
web/
├── app.py          # 应用创建、路由和依赖注入
├── parsers.py      # 唯一 Markdown 解析实现
├── static/
└── templates/
```

`app.py` 不再直接解析 Markdown，只调用 `parsers.py`。输出目录通过应用工厂或环境变量传入，测试可以使用临时目录。

### MVP 页面

只保留四个只读页面：

1. 作品概览
2. 人物列表与详情
3. 人物关系图谱
4. 事件时间线

### API 测试

至少覆盖：

- 无作品时返回空列表
- 作品概览统计正确
- 人物搜索正确
- 人物不存在时返回 404
- 图谱节点和边去重正确
- 时间线人物筛选正确
- Markdown 文件变化后缓存能够刷新

### 验收标准

- Web 层只有一套解析逻辑
- FastAPI TestClient/API 客户端测试通过
- 能读取 `data/output/平凡的世界` 的真实数据
- 大量节点时页面不会默认渲染全部低价值节点

## P1-2：统一模型供应商与配置命名

### 当前冲突

- 项目指令：小米 mimo-v2.5，通过 token-plan OpenAI 兼容 API
- 默认代码：`https://api.deepseek.com` 和 `deepseek-chat`
- 内部函数名仍包含 `_call_deepseek`
- 部署文档仍包含 DeepSeek 专用示例

### 推荐方案

将配置改为供应商无关命名：

```text
STORY_WIKI_API_KEY
STORY_WIKI_BASE_URL
STORY_WIKI_MODEL
```

代码层使用 `call_api` 或 `OpenAICompatibleClient` 等中性名称。默认值必须与项目当前实际使用方式一致；如果希望同时支持 DeepSeek 和 mimo，则通过 `.env.example` 给出两个配置示例，不在业务模块中写死供应商。

### 验收标准

- AGENTS.md、README、`.env.example`、部署文档和代码默认值一致
- 切换兼容供应商只需要修改环境变量
- 新增配置测试，验证自定义 base URL 和 model 能传递到请求层

## P2：巨型模块按业务边界逐步拆分

该任务只能在 P0/P1 完成后开始。

当前较大的模块包括：

| 模块 | 约行数 | 后续拆分方向 |
|---|---:|---|
| `generator.py` | 1424 | 卡片渲染、路径解析、索引/时间线生成 |
| `converter.py` | 1280 | EPUB、TXT、平台格式适配器 |
| `vault_manager.py` | 1061 | 扫描读取、查询、卡片写入 |

拆分原则：

- 按稳定业务职责拆，不以“文件不能超过多少行”为目标
- 每次只拆一个模块
- 拆分前先增加契约测试
- 不改变公开接口和输出格式
- 每次拆分后运行全量测试和端到端 smoke test

## 6. 风险与控制

| 风险 | 影响 | 控制方式 |
|---|---|---|
| 当前未提交改动较多 | 难以判断新旧问题来源 | 先分类现有改动，不覆盖用户已有工作 |
| 真实 AI 输出不稳定 | 端到端测试偶发失败 | 自动测试使用固定 mock，真实 API 另做手工验收 |
| Vault 路径写死 | 新环境运行失败 | 所有测试使用临时目录，正式路径使用环境变量 |
| Web 与生成器数据契约漂移 | 页面无数据或字段错误 | Web fixture 直接复用生成器产物 |
| 同时支持多个模型供应商 | 文档和配置再次分裂 | 保持 OpenAI 兼容接口和供应商无关命名 |
| 继续增加功能 | 基线长期无法完成 | v0.13.0 冻结新功能，胜利条件完成后再解冻 |

## 8. 阶段结束后的决策点

完成本方案后，再根据真实使用反馈从以下方向中只选择一个继续：

1. **分析体验优先**：图谱性能、检索和大型作品浏览
2. **创作质量优先**：人物一致性、章节反馈和人工审核闭环
3. **产品界面优先**：Web 中发起分析、查看进度和管理作品

不建议三个方向同时推进。下一阶段应由真实使用频率和痛点决定，而不是由当前功能清单决定。
